Проверка: включить тумблер, оставить машину на стоянке **отключённой от зарядки**, убедиться в непрерывных свежих `bydmate_live_snapshots` и строках `wifi keepalive` в daemon log **с 9-й по ~25-ю минуту**. **Тишина после 30-й минуты — корректное поведение**, а не отказ: закрывается окно wakelock (`PARKED_UNPLUGGED_WAKE_WINDOW_MS`). |

> **Почему B-10 не устарел после 0.5.2.** DiLink роняет WiFi через ~9 мин после
> парковки, а демон держит wakelock 30 мин. Без B-10 из этих 30 минут полезны
> первые 9, а оставшийся 21 минуту окно живёт впустую. Смысл пункта — сделать
> **всё** окно рабочим, а не «держать WiFi на стоянке» вообще.

## Решено не делать

Реестр обязательств хранит и отрицательные решения — иначе их придётся
переоткрывать. Дата — когда решение принято.

| Что | Дата | Почему |
|-----|------|--------|
| **Поле отправителя (`sender`) в payload** | 2026-08-12 | B-12 распознаёт отказ по `powerState` + каденсу, а это не требует ни изменения APK, ни согласованного деплоя двух репозиториев, и работает на **уже накопленных** данных (можно бэктестить). Поле сказало бы «почему» (демон перехватил поток), но для **обнаружения** не нужно. Осторожно при возврате к идее: `ingest-payload.ts` закрывает объект `.strip()` — новый ключ будет молча отброшен, а `source: z.literal("BYDMate")` отвергнет изменённое значение целиком. |
| **Автоматический гард на SQL-синтаксис pre-3.24** | 2026-08-12 | Ловит ровно один класс отказа. Правило зафиксировано в `CLAUDE.md` и в [ADR-0002](adr/0002-detect-telemetry-outage-by-symptom.md); обнаружение отдано B-12, который ловит **симптом**, а значит и следующий, ещё неизвестный, отказ цикла опроса. |
| **Аудит радиуса поражения цикла опроса** | 2026-08-12 | 0.5.2 уже изолировал три конкретные точки (запись SOC в собственный `try/catch`, маяк до `enqueue`). Полный аудит не взят: при живом B-12 следующая регрессия станет видна за минуты, а не за четыре дня. |
| **B-03 · Слияние истории при переименовании авто** | 2026-08-12 | Закрыт. Машина одна (`vehicle_id: way`), история рвётся только если владелец **сам** переименует её — то есть событие полностью контролируемо и его можно просто не наступать. L-объём кросс-репо работы ради этого не оправдан. Если переименование когда-нибудь понадобится — разовый SQL-`update` `vehicle_id` по таблицам телеметрии вместо машинерии слияния. |
| **B-04 · Аналитический экран в APK** | 2026-07-16 | APK — шлюз для облака. Презентация аналитики живёт в VoltFlow. |
| **B-07 · Полный порт `autoservice` / nativestack** | 2026-07-16 | Новых нужных данных не даёт; di+ остаётся необходимым каналом actuation. Имеющиеся BMS-поля (включая `kwh_charged`) — диагностические, для grid-side стоимости зарядки непригодны. Новые FID — только по доказательствам с конкретной машины. |
| **B-02 · Своя раздача обновлений** | 2026-07-16 | GitHub Releases уже работает (`UpdateChecker` → `releases/latest`); `mate_app_releases` — только для VoltFlow-web. |

> **Принцип (2026-07-16):** APK — **шлюз для облака**. Речь о *продуктовой поверхности,
> не о вычислениях*: аналитического **UI** в APK нет, но edge-вычисления и временная
> локальная БД для пред-агрегации/буфера — можно и полезно, **если это снижает
> нагрузку на облако**.
